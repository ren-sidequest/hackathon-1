# Candidate design QA

## Reference and scope

Compared the rendered Candidate pages against both original concept images and the written [Baseline](../../docs/product/EvidenceBridge_BASELINE.md) / [Blueprint](../../docs/product/EvidenceBridge_PRODUCT_BLUEPRINT.md). The workspace reference and rendered workspace were inspected together; the dual-role reference was inspected alongside application, task and status screenshots. HR implementation is outside this change.

The screenshots are generated by the Playwright `desktop page review and screenshot evidence` test in `tests/candidate.spec.ts`. They remain ignored under `test-results/candidate-desktop-page-review-and-screenshot-evidence/`, rather than being committed as application assets.

## Captures and checks

- Desktop: 1536 × 1000 viewport, full-page captures of application, tasks, populated workspace, work sample, process timeline, resources and submission status.
- Mobile: 390 × 844 viewport, full-page workspace capture; navigation, resource dialog and Escape tested.
- Actual Chromium interactions cover application validation, resource preview/download, chart filter, board CRUD, draft reload, notes, submission validation, read-only submitted work, review outcomes, reopening/resubmission, and reset.
- Console page errors are collected in both the end-to-end journey and screenshot walkthrough; both arrays were empty.
- Native dialogs provide modal focus handling and Escape dismissal; controls have accessible names and visible keyboard focus.

## Iterations

| Finding | Change | Result |
| --- | --- | --- |
| Initial compact labels were too small for presentation | Raised CSS captions to at least 12 px, board titles to 14 px, principal prose to 14 px; darkened key secondary text | Readable desktop resources, board and charts without horizontal page overflow |
| Animated chart capture could show axes before marks | Disabled chart entry animations | All 15 bar marks and the trend line render immediately in the workbench |
| Long board reasoning made cards difficult to scan | Two-line reasoning previews, with full content in editor and report | Four clearly grouped sections retain their sources and edit actions |
| Final report was too text-heavy relative to the concept | Added source-labelled channel and landing-page data exhibits when those sources are used by findings | Structured final output combines candidate reasoning, data and process evidence |
| Storage failure could still show a saved-draft message | Storage warning and in-tab-only save feedback | Simulated blocked storage still permits completion and download without falsely claiming persistence |
| Application title was a slogan | Changed to “Your application” and “About this role” | Core page headings describe the task |

## Accepted differences

- Uses the specified 224 px dark sidebar and Candidate green identity; analytical tabs/charts are blue. Does not copy the light sidebar or blue Candidate primary buttons in concept 2.
- The reference image compresses an entire app and annotations into one figure. The working app uses readable text and normal vertical scrolling, so a populated board may extend below the first desktop viewport. It preserves the three-column resources / analysis / investigation structure; narrower screens reflow it.
- At mobile widths resources are available through the Resources navigation, while analysis and the board stack vertically. This remains a desktop-first presentation.
- Uses the approved system font fallback, avoiding a network font requirement. Optional suggested duration replaces a fake countdown.
- Report downloads are Markdown and JSON; the app does not pretend to generate PDF. Linked-source visual exhibits remain visible in the browser.
- SQL/Python results and HR responses are explicitly labelled simulations. Timeline entries record actual local actions; loading sample findings adds a labelled demo event instead of fabricating an entire investigation.

## Result and limits

All six Candidate pages and the process-evidence view were visually inspected. No blocking layout/runtime issue was found in the reviewed desktop and mobile viewports. Local validation: 18 Vitest tests and 9 Playwright scenarios passed; TypeScript and production build passed. The build reports a roughly 681 KB uncompressed application chunk due to the chart library (about 201 KB gzip); this is retained as a known local-demo performance tradeoff.

This is visual and interaction QA for the local Candidate MVP, not an accessibility certification, a test of real hiring decisions, or a claim that the HR app, backend, AI extraction, or cross-machine synchronisation exists.
