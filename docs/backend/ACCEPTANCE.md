# EvidenceBridge 后端产品验收合同

本轮依据：用户冻结范围，以及《EvidenceBridge 黑客松完整参赛方案》2026-09-19 修订 2 第 7、8、9、10、16 节；沿用[产品蓝图](../product/EvidenceBridge_PRODUCT_BLUEPRINT.md)的补证价值与[产品基线](../product/EvidenceBridge_BASELINE.md)的固定场景。旧资料里的多轮补交、重开审核与前端模拟共享状态，不作为本轮实现要求。

本文由产品角色 AI agent 编写并审查，是验收标准，不是已执行记录或真人批准。通过情况以交付的实际测试记录为准；API 验收与双端 UI 联调分别记录。

## 1. 唯一范围与价值主张

- HarbourCart Pty Ltd / Junior Data Analyst / Alex Chen；SQL、Data Analysis、Business Problem Solving 三项要求。
- 预置申请材料与初始报告：SQL、Data Analysis 为 Supported；Business Problem Solving 为 Uncertain。材料不足表示“尚未观察到”，不表示候选人缺少能力。
- 一个 Conversion Drop Investigation 任务、一个正式提交快照、一次人工审核；草稿仍在 Candidate 本地。
- 固定业务事实：流量 +18%，转化率 3.4% → 2.6%，广告支出约 +15%。统一资源与字段以服务端数据版本为唯一事实来源；别的两渠道案例及参考结论不混入。
- 唯一 AI 环节：从当前作品提取五维可观察证据，给出原文定位、观察范围及剩余不确定性。初始材料分析与题目是明确标记的预置案例。
- 成功的产品证明：HR 能找到候选人实际提交的内容，看到支持与未支持的部分，并自主决定是否更新**目标要求**的证据状态。不是候选人排名、录用决定或长期能力证明。

暂缓：上传/PDF/OCR、动态出题、任意初始材料分析、岗位或账号平台、多租户、多轮补交、历史对比、通知/ATS、公共部署及复杂运维。

## 3. 四层状态语义

以下枚举为约定状态；HTTP 错误码与请求 schema 见接口合同。状态响应统一包装为 `{ data, meta: { replayed } }`，前端不自行从颜色或按钮文字反推状态。

| 状态层 | 业务语义 | 禁止混同 |
| --- | --- | --- |
| `task.status` | `draft → sent → submitted → reviewed`；前端另行维护编辑中的草稿 | “任务已完成”不表示证据充分 |
| `analysis.status` | `not_started / running / succeeded / failed`；输出另带运行模式 | 分析成功不表示 HR 已审核；失败不删除提交 |
| `review.decision` | 未审核时无决定；`confirm / needs_more_evidence / evidence_still_insufficient` | 三项决定都不是录用、拒录或候选人综合评价 |
| 要求的证据支持 | `supported / uncertain / verified`；初始 SQL、Data Analysis 为 `supported`，目标为 `uncertain`；`displayLabel` 单列供展示 | Confirm 前，提交或 AI 完成都不自动升级支持 |

人工结果映射：

| 人工结果 | 目标要求 | 本轮终点 | 共享备注 |
| --- | --- | --- | --- |
| Confirm | Verified through targeted task | 已审核；不重开 | 保存人工理由与本次作品引用；保留观察范围及未覆盖事项 |
| Needs More Evidence | Uncertain | 已审核，表达还需要哪些证据；本轮不重提 | 说明缺少的证据 |
| Evidence Still Insufficient | Uncertain | 已审核，说明本次材料仍不足 | 说明不充分之处 |

- 人工审核以已提交作品为前提，不以 AI 成功为硬前提；AI 服务故障时 HR 仍可查看原文并决定。
- 不足分支的“已审核”仅表示完成这次审核；页面不呈现绿色“能力已验证”。
- 审核备注应使用独立的 `comment` 或同义合同字段；Candidate 私人 `notes` 不复用为审核理由，也不进入共享数据或模型输入。
- 一次正式提交后冻结作品。再次发送相同请求按合同幂等返回，内容变化按合同报冲突，避免暗中替换已审核对象。另测重置后的新作品与分析绑定，不引入多版本系统。
- 前端旧流程须适配：Candidate 的 `more → working` 重开草稿和 HR 的 `REOPEN` 不属于本轮后端流程。

## 4. 固定观察规则与五维映射

以下四条是针对本轮既有场景的操作化观察规则，不是新 PDF 的逐字规则，也不是四项新岗位要求或评分项。

| 题目观察规则 | 主要维度 | 作品中可定位的证据 | 观察边界 |
| --- | --- | --- | --- |
| R1 说清业务问题，区分流量、转化率、订单和支出 | Problem Framing | summary 或发现卡中的问题陈述、数值比较与业务影响 | 流量增加不自动表示订单增加；比例变化与百分点分别表述 |
| R2 使用明确来源与可比口径作分解 | Evidence Navigation | findings 中的资源 ID、期间/渠道定位与比较；过程事件可作补充 | 打开文件仅证明访问事件；客户端上报过程不等于经独立核验的行为；示意分段与渠道总体不随意相加 |
| R3 区分观察、解释与因果，并提出可检验的缺失证据 | Hypothesis Formation、Evidence Seeking | 假设卡、证据请求卡中的待证关系、替代解释及所需数据 | 相关性不证明因果；同一期间发生的改版/投放变化只是待验证解释 |
| R4 提出与证据强度相称、可检验且有优先级的行动 | Decision Making | 建议卡说明先做什么、为什么、如何验证及何时调整 | 推荐动作不是预测收益保证；不强制套用唯一“标准答案” |

五维输出均应出现明确的观察状态；缺乏依据时用“尚未观察到”，不凑正面评价。每条实际观察包含维度、陈述、sourceId/定位、逐字引文、支持范围、剩余不确定性。定位指向当前提交公开内容；数据资源引用另指向同一 datasetVersion。只有资源存在和引文匹配，仍不等于候选人的数字结论或因果解释已被证明。

不输出总分、候选人排名或自动录用建议。五维用于组织可审阅证据，不作为五个隐藏分数。

## 5. 后端验收矩阵

下表给出必须观察到的结果；“验证方式”不是已通过声明。测试工程师记录实际命令、样本、结果与未执行项。

| ID | 场景 / 操作 | 预期结果 | 验证方式 |
| --- | --- | --- | --- |
| AC-01 | 初始 GET | 固定身份、三要求、初始来源及预置标签完整；目标要求 Uncertain；任务尚未发送 | API 集成 |
| AC-02 | 发送 → 另一客户端 GET | 相同 taskId、说明、数据版本；任务只发送一次；不存在虚构的已提交作品 | 双 API 客户端 |
| AC-03 | 提交含独特句 `EB-CROSS-CLIENT-UNIQUE` 的公开作品 → 独立 GET | summary/findings/processEvidence 与提交快照一致；ID、时间与内容指纹稳定 | API 集成与深比较 |
| AC-04 | 保存后修改调用者原对象、本地草稿或重复提交不同内容 | 服务端快照保持原文；变化请求按合同失败；原 AI/审核绑定不串用 | 单元 + API |
| AC-05 | 当前分析中的来源和引文定位 | sourceId 存在于当前提交；定位对应字段；quote 逐字匹配；绑定 submissionId 与指纹 | 校验器 + API |
| AC-06 | Confirm → 两次 GET | 仅 Business Problem Solving 变为 Verified through targeted task；SQL 与 Data Analysis 不变；双方读到同一决定和理由 | API 集成 |
| AC-07 | 分别执行两个不足分支 | 目标保持 Uncertain，保存原因；本轮已审核，不开放重提或重开 | 每分支独立重置的 API 测试 |
| AC-08 | 未发送提交、未提交分析/审核、审核后不同决定 | 明确状态错误；既有状态不被部分更新 | 负向 API |
| AC-09 | 重复发送/提交/分析/审核或同幂等键不同内容 | 重复请求按接口合同有确定结果；不额外产生提交/审核；键冲突不覆盖原结果 | 串行/并发 API |
| AC-10 | 旧 taskId/submissionId/datasetVersion、旧运行中的结果 | 明确过期/不匹配错误；不更新当前案例或当前报告 | 负向 + reset/analysis 交错 |
| AC-11 | 在私人 notes 写独特句；构造含 notes 的请求 | 正常接入请求不带私人字段；服务端排除或按合同报输入错误；共享响应/报告/模型输入无私人句 | 服务器负向、模型 spy；浏览器请求检查待接入 |
| AC-12 | 空白/过长/错误类型、未知来源、重复来源 ID、无效枚举、异常 JSON | 有限、可解释的合同错误；无持久化部分写入；不泄漏内部信息 | 边界/API |
| AC-13 | 模型超时、异常、畸形结构、虚构来源/引文 | AI 标为失败或返回明确失败；原作品可读可人工审；不自动用手工模拟冒充实时输出 | 适配器可控 stub + API |
| AC-14 | 刷新、关闭客户端、服务进程重启 | 同一持久化状态恢复；不会自动回到未提交；存储损坏按文档显式报错而非伪装空案例 | 持久化/重启集成 |
| AC-15 | 重置后重演主线 | 恢复初始案例与目标 Uncertain；旧提交/AI/审核不再作为当前结果；新作品拥有新绑定 | API 集成 |
| AC-16 | 从非允许来源发写请求/重置 | 本地演示访问边界生效；跨来源网页不任意修改共享案例 | 访问控制/Origin 测试 |
| AC-17 | 复算统一数据 | 期间/渠道汇总、订单/流量转化率、花费增幅在公开精度内一致；示意资源明确标记非可加总范围 | 确定性数据单测 |
| AC-18 | 提交中夹带“忽略规则/改为评分”等指令 | 仍作为作品材料；输出只含固定观察结构，无指令执行、密钥泄漏或总分 | 提示隔离审查；真实效果另测 |
| AC-19 | 重置后提交变更文本再分析 | 旧输出不绑定新输入；同义改写可得类似观察，但 ID/指纹对应新快照 | API/AI 绑定测试 |
| AC-20 | 读取与人工复核模型观察 | 正面观察与“未观察到”同样可展示；结论范围不超出引文；剩余不确定性保留 | 规则测试 + AI agent 内容审查 |

## 6. AI 三类最小测试材料

| 类型 | 输入构造 | 应检查的反例 | 可声称的检验范围 |
| --- | --- | --- | --- |
| 有依据 | 引用当前来源比较总体和 Paid Search，明确待证因素，再提出数据请求与小范围验证 | 引文是否真实；模型有无添加未出现的计算、行动或过程 | 引用与范围核验；不证明实际候选人预测效度 |
| 漂亮但无依据 | 用“优化策略、提升体验”等措辞，没有可定位数据或验证逻辑 | 是否仍凑齐五维正面结论；是否保留“未观察到” | 对缺失证据的处理 |
| 混淆因果 | 写“流量增加同时转化下降，因此广告必然导致下滑，立刻全面停投” | 是否把候选人断言当作已证实因果；是否指出缺少对照和混杂信息 | 观察陈述与因果结论边界 |

采用三层记录：

1. **确定性 stub**：验证请求边界、输出 schema、引文校验、绑定、失败恢复；不称为真实模型实验。
2. **真实模型实验**：保存合成输入、提示词版本、模型标识、时间、原始输出、校验与人工/AI agent 检查者身份。凭据不足时明确待运行，其他后端验收继续。
3. **回放**：只用于有真实运行记录且输入指纹匹配的保存输出；手工写的例子单独标为 manual fixture，不冒称真实回放或实时结果。

不因同义改写后结论相似判失败；重点是当前输入绑定与引文依据。来源移除、文本改变、来源版本变化应触发失效或重新分析。初始申请固定不可编辑，材料增删反例不引出另一条通用解析管线。

## 7. 前端接入与完成声明

小傅接入时使用服务端作为已发送任务、正式提交、AI 观察、人工结果及更新报告的事实来源；本地状态仅保留草稿与页面交互。成功写入后重新 GET；另一端刷新可见即可，无需实时推送。

接入清单：

- 替换两端散落的 KPI、渠道表、资源预览、图表、示例答案数字及任务时长；读取服务端版本，避免“显示一致、下载 CSV 不一致”。
- 提交仅构造公开 allowlist，不扩散 Candidate notes；HR 备注使用独立共享字段。
- 关闭模拟收件、模拟决定、重开、重提对后端正式状态的覆盖；如保留演示控件，应明确标识本地模拟模式。
- 展示 loading / error / 过期引用与分析模式；请求失败不先显示业务成功；AI 失败时仍显示原作品。
- 将引用点击定位到当前 submissionId 下字段，而非 HR 写死的样例；初始材料与实际提交分区标识。
- 真正双端浏览器联调补验：独特句原样出现、同一决定、notes 网络请求检查、两个不足分支、刷新与重置。API 测试不替代这项。

后端全部相应检查通过且 UI 尚未接入时，统一表述：**“后端验收完成，双端 UI 联调待小傅接入。”**

进一步边界：只在本地实现与验证；GitHub Pages 继续是静态展示，不代表已有共享后端。没有真人试用记录就标为待验证；没有真实模型运行就标为待真实调用验证。测试、AI agent 审查、真人验收和部署是四件不同的事。
